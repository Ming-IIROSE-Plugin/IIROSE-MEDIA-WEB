- (direction) User Ming requested cloud sync for the existing local favorites system, proposing the host-site user identity as the storage key
- (decision) Live runtime probe on iirose.com confirmed window.uid is readable inside the messages.html iframe where the plugin runs
- (decision) window.uid is account-bound and stable: cleared host localStorage, logged out, logged back in and uid was byte-identical, so it is a valid storage key but a semi-public identifier, never a credential
- (constraint) Host localStorage 'cookie' holds the account password MD5; it must never be used as a credential, key, or server-side secret
- (direction) User approved Option A: uid partitioned storage plus end-to-end encryption with a user-chosen sync passphrase
- (direction) User approved merge as the first-enable conflict default
- (direction) User chose Tencent Cloud as backend: a new dedicated SCF function backed by object storage (COS), separate from the existing bundle-hosting function
- (direction) User approved the anti-abuse design of three gates: key-space whitelist, rate and quota caps, and tamper rollback via COS versioning
- (decision) New function IIROSE-MEDIA-SYNC in ap-guangzhou, deployed by a new scripts/deploy_sync.py on the existing GitHub Actions pattern, keeping deploy failure isolated from bundle hosting
- (constraint) SCF function URL auth offers only CAM auth (requires cloud keys in the browser, unacceptable) or public; therefore public is mandatory and all abuse control must live inside the function
- (constraint) SCF API Gateway triggers are retired; the HTTP entry point must be a function URL
- (decision) Coarse rate and quota limits were rejected as user-hostile: caps are set loose and a breach returns a readable prompt telling the user to contact the maintainer (Ming) instead of hard blocking
- (decision) Snapshot size cap 512KB with no item-count cap, to stay inside the free tier for the first release
- (decision) COS bucket versioning is enabled as rollback insurance against a bad or malicious overwrite
- (constraint) No paid SCF packages or resource bundles will be purchased; every rate cap must be sized for a zero-cost target and cost alerts must be configured
- (decision) Key derivation is PBKDF2-SHA256 with 310000 iterations over the sync passphrase; the passphrase never leaves the client
- (decision) Payload encryption is AES-GCM-256 with a random 12-byte IV per write and additional authenticated data binding uid, envelope version and updatedAt
- (decision) No passphrase recovery will be offered; the UI must state that forgetting it makes cloud favorites unrecoverable
- (decision) Argon2id was rejected as it needs a WASM payload; native WebCrypto PBKDF2 keeps the bundle lean, consistent with the boring-technology principle
- (decision) Merge key is the existing device-independent composite favorite id platform:type:rawId, which needs no new identity scheme
- (decision) On first enable: pull, union with local by composite key, and on the same key keep the earliest createdAt to preserve first-favorited time; a preview dialog must be confirmed before upload
- (decision) Steady state uses whole-snapshot last-write-wins keyed on updatedAt, deliberately simple and explainable for v1
- (decision) Deletes become tombstones (deletedAt) that participate in merge, otherwise a delete on device A is resurrected by device B; tombstones are physically purged after 30 days
- (decision) Sync triggers are change-driven only: writes debounce 5s per session, reads happen on activation plus manual sync; chosen over polling to keep request volume near zero
- (capability) CAP-1: Sync Identity and Key Unlock - Enable sync with the host account uid plus a user-chosen passphrase, deriving the key locally
- (capability) CAP-2: Encrypted Snapshot Upload and Download - Serialize favorites into an encrypted envelope, PUT it, and later GET and decrypt it back into local records
- (capability) CAP-3: First-Enable Merge with Preview - Union local and cloud by composite key, keep earliest createdAt, show counts and require confirmation
- (capability) CAP-4: Deletion Propagation via Tombstones - Deletes sync as tombstones and survive merges without resurrection
- (capability) CAP-5: Change-Driven Auto Sync plus Manual Sync - Debounced upload on change, pull on activation, manual sync button, no polling
- (capability) CAP-6: Quota and Failure Feedback - Readable prompts for oversize snapshots, rate limits, wrong passphrase, and offline conditions
- (capability) CAP-7: Cloud Data Control - Show last sync time, wipe cloud copy, and disable sync while keeping local data
- (constraint) Server is zero-knowledge: no plaintext favorites and no passphrase may be stored, logged, or forwarded, and request bodies must not be logged to CLS
- (constraint) Object keys are generated server-side only as sync/{uid[0:2]}/{uid}.json with a hex uid whitelist, so the function can never act as a general file or image host
- (constraint) Bucket is private read-write with no public direct link and function role access limited to the sync prefix
- (constraint) Only logged-in accounts with a stable uid may sync; guests must not upload
- (constraint) Client requests must not be routed through the existing window.iirosemedia.cors proxy
- (constraint) No polling, no persistent connections, no per-record endpoints
- (constraint) No new heavy crypto dependency: WebCrypto only
- (constraint) Sync UI must follow the repo mobile conventions: 44px and 48px touch targets, max-[768px] breakpoint, and the 300ms buildSelect2 inter-dialog delay
- (constraint) The IndexedDB store must be upgraded in place from version 1 to 2 with new sync fields and no data rebuild

- (assumption) Assumes per-user favorites stay in the low thousands, so a 512KB envelope is sufficient
