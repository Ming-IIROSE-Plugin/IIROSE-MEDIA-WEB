# 运行时验证观察（SPEC-netease-search-failover）

- 验证日期：2026-10-19
- 环境：iirose.com 真实站点 + `dist/bundle.js` 注入 `messages.html` iframe（Chromium，桌面 1440×900）
- 测试账号：本机 `.secrets/`（不入库）

## 结论

统一入口 `SendFetch.neteaseRequest` 在真实链路上按预期工作，全部 5 条 CAP 均有实测证据：

| 场景 | 构造方式 | 观察结果 |
|---|---|---|
| 正常请求 | 默认（广州） | 仅广州 1 次请求，`code=200`，歌单搜索 1/46 出卡片，无提示 |
| 风控码换节点（FM-1） | 拦截广州响应为 HTTP 200 + `{"code":-462}` | 广州 → 香港，香港 `code=200`，歌单/专辑正常出卡片，无提示；第二次搜索仍先打广州（无粘住） |
| 433 网关超时换节点（FM-2） | 拦截广州响应为 HTTP 433 | 广州 → 香港，结果正常，无提示；第二次搜索仍先打广州 |
| 假 200 非 JSON | 广州返回 `<html>not json</html>` | 判失败 → 香港成功，无提示 |
| 假 200 其它业务码 | 广州返回 `{"code":4041}` | 判失败 → 香港成功，无提示 |
| 节点挂起 | 拦截广州请求永不响应 | 5.0s 处 `ERR_ABORTED`（AbortController 生效），随即转香港并成功，无提示 |
| 全部节点挂起 | 广州 + 香港均永不响应 | 5s + 5s 两次中止后 toast「网易云请求超时，请稍后重试或切换节点」1 次，列表空态「什么也没有搜到...」 |
| 全部节点风控 | 两节点均返回 `code:-462` | toast「网易云风控校验，请稍后重试或切换节点」1 次，空态 |
| 全部节点 433 | 两节点均 HTTP 433 | toast「网易云请求超时，请稍后重试或切换节点」1 次，空态 |
| 网络错误 | 两节点均拦截并 abort | toast「网易云网络请求失败，请检查网络后重试」1 次，空态 |
| 切换 HK | `neteaseSetting.api = "HK"` | 请求出口为 `ap-hongkong.tencentscf.com`，结果正常 |
| Dev 模式 | `neteaseSetting.api = "Dev"` | 仅请求 `http://localhost:9000`（单节点，不回落 SCF），失败后 toast 1 次 |
| 详情链路 | 歌单「选歌」/专辑「选歌」 | `/api/v6/playlist/detail`、`/weapi/v1/album/{id}`、`/api/song/detail` 均 `code=200`，多页列表渲染正常，无提示 |
| 搜歌并点播 | 搜索音乐 → 播放 | `m__4@0>...` 与 `&1{"s":...,"d":238.698}` 正常发出，无提示 |

`verifyUrl` 未在任何提示或 UI 中出现。

## 「歌单/专辑 vs 搜歌」失败触发频率

- 本窗口内真实广州节点结果：歌单搜索 3 次中 1 次失败（静默切香港成功，用户无感）；专辑搜索、搜歌各 1 次均直接成功；**未在窗口内复现 HTTP 433**。
- 样本量过小，既不能证实也不能推翻「歌单/专辑更易触发」的推断。可以确认的是：失败检测与重试入口对四个端点完全一致（同一 `neteaseRequest`），因此该假设是否成立都不影响覆盖率。
- 另有一次真实广州请求在点击播放链路中静默切换香港成功（同上，未弹提示）。
