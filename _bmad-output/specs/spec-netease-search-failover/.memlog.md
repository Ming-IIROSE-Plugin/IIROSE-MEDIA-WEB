topic: 网易云搜索失败检测与代理切换重试（风控 -462 / SCF 超时 433）
updated: 2026-10-19T21:06
---

- (note) 输入：两个线上错误场景。① /weapi/search/get 返回 HTTP 200 + code:-462、verifyType:40（st.music.163.com 加密页验证），代理出口 IP 被网易云标记风控；② 腾讯 SCF 网关 HTTP 433 'Invoking task timed out after 3 seconds'（云函数 3 秒超时强杀）。均多发于搜索歌单/专辑。
- (note) 代码调查：NeteaseSearch/index.ts 只判 response.ok、从不读 data.code，风控发生时 result 为 undefined → 静默空列表；sendPost 无 AbortSignal 超时无重试；SendFetch.cors 静态块在 Environment.setEnv 之前求值，阿里云代理选择对网易云实际不生效，流量恒走广州 SCF。
- (decision) 根因结论：情况1是网易云反爬风控（IP 级），verifyUrl 绑定代理出口 IP，用户在浏览器验证无效，唯一出路是换出口；情况2是 SCF 网关 3 秒函数超时，非网易云返回，常因风控慢响应+大响应体触发。
- (decision) Ming 拍板：风控码（-462 等）检测到后自动切换备用代理重试一次，成功则本次会话后续网易云请求继续用备用代理，仍失败提示用户；所有网易云请求加超时，433/超时/网络失败同样换代理重试一次。
- (decision) Ming 拍板：不修 Environment 静态块竞态（影响全部平台流量，另行立项），备用代理直接硬编码进重试逻辑（SendFetch.malaysiacors 香港 SCF 实例）；失败必须 toast 明示原因，区分『真无结果』与『请求失败』。
- (constraint) 重试只重试一次，不做循环重试（避免加重风控）；代理切换仅会话级内存态，不持久化、不新增设置项；提示复用宿站 ShowMessage，不引入新 UI。
- (constraint) 不引导用户打开 verifyUrl（验证绑定代理出口 IP，用户侧完成也无法解除代理 IP 封禁）；改动范围限网易云 API 层与调用处，不动其它平台请求逻辑。
- (capability) CAP-1 业务错误码检测：网易云响应解析时必须检查 data.code，识别 -462/-460 等风控码为独立失败类型，不再与空结果混淆。
- (capability) CAP-2 风控自动换代理：检测到风控码后自动换备用代理（香港 SCF）重试同一请求一次；成功则本次会话后续网易云请求沿用备用代理。
- (capability) CAP-3 超时与传输失败处理：网易云所有出网请求带 AbortSignal 超时；超时/HTTP 433/网络错误自动换备用代理重试一次，仍失败进入提示路径。
- (capability) CAP-4 失败明确提示：所有失败路径（风控/超时/网络）toast 说明原因，用户可区分『无结果』与『请求失败』。
- (assumption) 歌单/专辑高发为推断：type=1000/10 响应体远大于搜歌，链路连带 /api/v6/playlist/detail?n=100000 巨型请求，更易触发风控与 3s 超时；未实测验证。
- (assumption) 香港 SCF 与广州 SCF 同构（同为 /proxy?url= 转发），重试可直接复用现有 sendPost 请求层。
- (question) 前端 AbortSignal 超时阈值取多少？SCF 网关本身 3 秒超时，前端阈值应明显大于 3s（建议 10s）避免误判网关超时为前端超时。
- (question) 会话内切到香港备用代理后，广州 SCF 恢复时要不要切回？简单做法是会话内不切回（刷新回默认），待定。
- (event) Pass 1 coherence：8 项 Spec Law 通过——4 个 capability 均 intent+success 齐备；约束均可裁剪设计（一次重试、硬编码备用代理、会话级切换、禁展示 verifyUrl）；4 个 non-goal；成功信号可实测。
- (event) Pass 2 preservation：两个错误场景的响应样本/识别特征/处理动作全部落入 failure-modes.md companion；「多发于歌单/专辑」以假设保留；用户四项拍板全部落约束与 capability；仅丢弃原始样本中的 verifyToken/params 等无载荷细节。spec rendered & validated.
- (note) Ming 补充关键事实：失败是概率性的——同一节点失败后，下一次请求大概率成功。因此不做会话级粘住备用代理。
- (decision) Ming 拍板（推翻会话粘住方案）：节点1（广州 SCF）永远优先；某次请求失败后仅该请求轮询备用节点（香港）重试；每一次新请求仍从节点1开始，再失败再轮询备用。
- (decision) Ming 拍板：前端 AbortSignal 超时阈值定为 5 秒。
- (direction) Ming 要求：「多发于歌单/专辑」不再停留为假设——实现后的运行时验证环节必须实测（对比搜歌单/专辑 vs 搜歌的失败触发频率），结果回写 spec。
- (decision) Ming 确认：香港备用 SCF 与广州同构、可复用 sendPost 的假设成立，不再是假设。
- (event) 更新后重渲染并复检通过：CAP-2 改为无粘住的节点轮询（节点1 优先、失败当次换备用、新请求回节点1）；超时 5s 落入 CAP-3 与 companion；两个 open question 全部解决清空；香港同构假设升级为已确认事实；「歌单/专辑高发」转为运行时验证必测项写入 Success signal。Pass 1 + Pass 2 均通过。
- (decision) Ming 拍板（推翻『不新增设置项』）：网易云设置页新增『优先节点』选项，节点1 = 用户所选节点（默认广州 SCF），失败重试走另一节点。沿用 B 站既有模式：localStorage 平台设置（bilibiliSetting.api / getBilibiliCors 同构），NeteaseSetting 预留的 api 字段从字面量 "default" 扩为节点枚举。
- (capability) CAP-5 优先节点设置：用户可在网易云设置中选择优先节点（广州/香港，默认广州），选择持久化；节点1 即该设置值，CAP-2/3 的重试链以它为起点。
- (constraint) 设置项沿用现有平台设置模式（localStorage，参照 bilibiliSetting.api 与 getBilibiliCors 的请求时读取），不引入新 UI 体系；候选节点限广州/香港两个现有 SCF 实例（含 Dev 本地实例可仿 B 站可选，非必须）。
- (note) Ming 修订：推翻此前「不持久化代理选择、不新增设置项」的约束——用户应能在设置里选择优先节点，节点1 即该用户选定节点。
- (decision) Ming 拍板：新增用户设置项「网易云优先节点」（广州/香港可选，默认广州 SCF），持久化；轮询链中的节点1 定义改为『用户选定的优先节点』，其余轮询规则不变——每次新请求从优先节点开始，失败当次才轮询其余节点。
- (capability) CAP-5 优先节点可选：用户可在网易云平台设置中选择优先节点（广州/香港，默认广州），选择持久化，重试链以该选择为节点1。
- (constraint) 节点选择设置项放在网易云平台设置（src/settings/ 体系），与 quality/lyricOption 同级管理；默认值必须为广州 SCF，不选择时行为与改动前一致。
- (event) 发现并行会话对同一需求（设置里选优先节点）写了重复的 CAP-5 与约束（memlog 29-31）；本会话核实其 bilibiliSetting.api / getBilibiliCors 引用属实（src/Api/index.ts:290，请求时读 localStorage）后合并去重：CAP-5 单一化，约束保留 B 站同构模式 + quality/lyricOption 同级管理，『不新增设置项』non-goal 移除，Success signal 与 companion 节点链改为『优先节点=用户设置（默认广州）』。Pass 1+2 复检通过。等待 Ming 下达 build 指令再进入实现。
- (note) Ming 追问 -462 的 verifyUrl 用户完成验证是否可行。结论：不可行（共享 SCF 出口 IP 下机会为零）——验证绑定代理 IP 而非用户、weapi 请求不携带用户 cookie 无凭证回传、共享 IP 信誉由全体用户行为决定；唯一有效场景是用户本机自建代理（同 IP）。确认维持「不展示 verifyUrl」约束，工程重心放换节点重试。
