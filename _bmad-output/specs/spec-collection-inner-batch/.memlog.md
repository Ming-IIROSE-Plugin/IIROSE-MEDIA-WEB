- (direction) 用户调用 bmad-spec 提三项：①收藏里歌单/专辑点「查看」进内页后只有单首点播与全部播放，挑不了2/3/10首；②万首歌单点查看后循环发很多次请求才显示，要先取一段、翻页到末尾再取；③批量点播200首点「中断」后房间不再发歌，但网络面板里请求仍在发。
- (decision) slug 取 collection-inner-batch；交互模式，读代码定位根因后起草，三处取舍经用户问答确认。
- (note) 根因①：CollectionHeader 只有「全部播放」→OrderMenu(正序/乱序)，内页 currentOnDemandPlay=NetEasePlatform.MOD 逐首点播；选集面板只在点播弹窗 buildSelect 的选项2里，内页无多选入口。
- (note) 根因②：switchToMultiPage → getSongListMultiPageData → processSongPlatformData(全部 trackIds) → getNeteaseSongDetail 按100一批串行取完全部详情才返回首屏；万首=约100次串行请求（失败节点再各重试）。内页每页 itemPerPage=10，分页是 allMediaData 本地切片。专辑同走 processSongPlatformData。
- (note) 根因③：sendSongs 先 getNeteaseSongDetail(全部ids) 串行取完才进发送循环，这段期间不查 batch.cancelled；neteaseRequest 不接外部 AbortSignal，飞行中请求无法中止；BatchProgress.remove() 在停止后约1.4s(STOP_LINGER+LEAVE)从 cancelled 集合删掉 id，handle.cancelled 随之变回 false——准备阶段停止的批次详情取完后会照常开始发歌（潜在复活缺陷）。
- (decision) 问题1形态：用户选「列表内直接多选」，不选「内页头加选集按钮打开选集面板」。
- (decision) 问题2粒度：每段100首（一次详情请求）；进内页只取首段即显示，总页数按 trackIds 立即算出；翻到已取范围末页时预取下一段，跳页时按需取对应段。
- (decision) 问题3范围：停止后立即中止该批次全部网络活动——不再发起新请求，飞行中的请求 abort；并修停止标记被清除导致循环复活的隐患。
- (capability) CAP-1 intent：用户在歌单/专辑内页直接勾选任意多首、按点选顺序一次点播。success：内页可进入/退出多选；行显示点选序号，跨分页保留选择；底部显示已选数并可清空、点播所选；点播按点选顺序发出，单首走单曲播报、多首走批量进度浮窗并可停止；退出内页或多选即清空。
- (capability) CAP-2 intent：上万首歌单的内页快速出首屏，曲目详情按需分段取回。success：进内页到首屏只发1次歌单详情+1次歌曲详情（≤100首）；分页显示按 trackIds 算出的总页数；翻页只在越过已取范围时取对应100首段，末页预取下一段；同一段不重复请求；取段失败该页显示可重试状态；退出内页中止未完成的段请求。
- (capability) CAP-3 intent：用户停止批量点播后，该批次立即且永久停止全部发送与网络请求。success：点停止后不再发出任何点播报文，也不再发起该批次的详情/歌词请求，飞行中请求被 abort；停止标记在浮窗收起后仍有效，准备阶段停止的批次不会在详情取回后复活；单元测试覆盖准备中停止与发送中停止两条路径。
- (capability) CAP-4 intent：整张点播与多选点播不再为大歌单预先取完全部详情才开始发送。success：批量发送按100首分段边取详情边发，第一首在首段详情到达后即发出；每段请求前检查停止；发送顺序与入参顺序一致（正序/乱序/点选顺序）。
- (constraint) 网易云请求一律经 SendFetch.neteaseRequest；为支持中止，给它加可选外部 AbortSignal，外部中止与5s超时区分：外部中止不换节点重试、不弹失败提示、返回 null。
- (constraint) 多选点播入口必须包 guardedRequest；批量用 startBatch/finalODSONG 与 runBatchAnnounce，单首用 runSingleAnnounce，与选集面板一致；不得回到 buildSelect2 或跨弹窗 setTimeout(300)。
- (constraint) 多选 UI 只拼 tokens.ts 令牌与 DeskIcon；手机可点目标≥44px、断点 max-[768px]；层级纳入 overlayLayers 互斥规则；房间不支持点播时「点播所选」灰化。
- (constraint) 分段加载保留现有内页契约：分页仍为每页10首、页码 01 / NN、列表/网格视图切换、内页头曲目数；歌单以 trackIds 为完整列表与顺序，不只读 tracks。
- (constraint) 停止标记必须对该 handle 永久有效（与浮窗卡片的移除解耦）；BatchProgress 现有测试语义（已停止不被 step 改回进行中、停止后快速收起）保持。
- (assumption) 多选的点选顺序、序号徽章、正序发送与选集面板语义一致；本轮不在多选里提供乱序（整张乱序仍走全部播放）。
- (assumption) 多选只能选已取回的曲目（看得到才能选）；多选模式在列表与网格两种视图都可用。
- (assumption) 范围覆盖所有歌单/专辑内页（收藏与搜索进入的共用同一内页），不只收藏。
- (assumption) 多选数量不设上限；超过一页的选择依赖跨页保留。
- (question) 多选入口放哪：内页头「多选」按钮，还是长按/行首勾选框直接进入？手机端底部「点播所选」条与迷你条如何并存？
- (nongoal) 不改选集面板（episode-picker）本身与点播弹窗的正序/乱序/选集一级菜单。
- (nongoal) 不做 B 站多P、视频合集内页的多选与分段加载；不做跨会话保存多选。
- (nongoal) 不撤回停止前已发出的点播；不中止宿站自身的媒体加载请求（只管插件发起的请求）。
- (event) Pass1 Coherence：4 个 CAP 均有 intent+success，约束均排除具体做法，非目标3条，成功信号可演示；通过。
- (event) Pass2 Preservation：三条用户诉求分别落 CAP-1/CAP-2/CAP-3，代码根因入 brownfield.md，CAP-4 来自根因③（大批量预取全部详情）；无遗漏。
- (direction) 用户确认四条假设成立：多选只按点选顺序、无乱序；只能选已显示的歌，列表与网格都可多选；覆盖所有歌单/专辑内页；不设数量上限。
- (decision) 多选入口：每行（及网格卡）前直接放勾选框，无独立多选模式；勾任一首即进入选择态，清空即退出。取代 CAP-1 的「进入/退出多选」表述。
- (decision) 手机底部条（用户授权由我决定）：已选≥1时「点播所选」条占用迷你条的位置（同位同高、在标签栏之上），迷你条暂时隐藏，清空或点播后恢复；桌面同理占用底部条位置。理由：不叠两条压缩列表高度，也不新增浮层层级。
- (capability) CAP-1（修订）intent：用户在歌单/专辑内页直接勾选任意多首，按点选顺序一次点播。success：每行与网格卡前有勾选框，勾选即显示点选序号，跨分页保留；已选≥1时选择条取代底部条/迷你条，显示已选数、清空、点播所选；按点选顺序发出，单首走单曲播报、多首走批量进度浮窗且可停止；点播后、退出内页或清空即恢复底部条。
- (constraint) 勾选框可点区域在手机≥44px，点勾选框不触发行点播；手机曲目行加勾选框后标题仍须单行可读。
