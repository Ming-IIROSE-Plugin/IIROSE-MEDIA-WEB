# 后端架构与抗滥用 (backend-architecture.md)

SPEC.md 中后端相关约束的落地。协议见 `sync-protocol.md`，加密见 `crypto-spec.md`。

## 1. 拓扑

```
[插件 · messages.html iframe]
   window.uid ──► 分区键
   同步口令 ──► PBKDF2 ──► AES-GCM（本地，口令不出端）
   IndexedDB favorites ◄──► 加密信封
                │
                │  HTTPS，直连（不经 window.iirosemedia.cors 代理）
                ▼
   [SCF 函数 URL]  IIROSE-MEDIA-SYNC  · ap-guangzhou · 开放鉴权
        · uid 白名单校验  · 键派生  · 尺寸/频率/日配额门禁  · 零日志
                │  只调用 PutObject / GetObject / HeadObject
                ▼
   [COS 私有桶]  sync/{uid[0:2]}/{uid}.json   · 版本控制开启
```

**为什么新开一个函数而不是复用 `IIROSE-MEDIA-WEB`**：后者在托管前端 bundle 并充当 CORS 代理，任何同步侧的异常、超时或并发挤占都会连带插件加载一起挂。`scripts/deploy_scf.py` 的产物替换逻辑与同步函数的部署形态也不同，混在一起会让 CI 互相牵扯。新函数独立部署、独立限额、独立告警。

**入口形态**：必须用**函数 URL**。SCF 的 API 网关触发器已下线。

**鉴权**：只能用「开放」。函数 URL 的另一档「CAM 鉴权」要求调用方持有腾讯云密钥做 TC3 签名——浏览器端不可能安全持有，直接排除。**所有抗滥用逻辑因此必须在函数内部自建**（第 4 节）。

## 2. 对象键与权限

**桶策略：新建一个专用 COS 桶**（与既有资源隔离，便于独立设生命周期与告警口径）。

> **为何不用维护者已有的「文件存储」**：账号里那份 `IIROSE-WEB-MEDIA`（CFS）是 POSIX 文件系统，不是对象存储。用它需要把函数放进 VPC 并保证挂载点同可用区，且 **CFS 没有原生版本控制**——回滚兜底这条硬约束无法满足，只能自造版本机制；同时 NFS 对同一文件的并发写语义较弱。COF 更适合别的用途，同步走 COS。

- 建桶后立即：设**私有读写**、**开启版本控制**、配 `sync/` 前缀限定的生命周期规则。

- 键布局：`sync/{uid[0:2].toLowerCase()}/{uid}.json`，两级前缀避免单前缀热点。
- uid 白名单：`^[0-9a-f]{8,32}$`（实测宿站 uid 为 13 位 hex，放宽以容忍格式演进）。不合法立即 400。
- 函数**不接受客户端传入的键**——键完全由 uid 派生，客户端无法指定任意对象路径。
- 函数角色最小权限：仅允许该桶 `sync/` 前缀的 `PutObject`、`GetObject`、`HeadObject`；不授予列举、删除、跨桶权限。**不要图省事直接复用 `SCF_QcsRole`**——它通常带整桶甚至全 COS 权限，会让「只碰 sync/ 前缀」这条约束形同虚设。
- 桶本身已是私有读写，**不修改桶策略**；不开公网直链。
- 对象 `Content-Type` 固定 `application/json`，并写 `Cache-Control: no-store`（避免中间层缓存密文）。
- 生命周期规则**必须用前缀限定到 `sync/`**，否则会波及该桶内维护者的其他数据。

## 3. 版本控制与回滚

**版本控制是什么（给运维看的白话版）**：COS 默认「同名覆盖即销毁」——往同一个对象键再写一次，旧内容直接消失。开启版本控制后，每次覆盖都会把**旧内容存成一个历史版本**，对象键不变，但你随时能按版本号取回上一版。类比：普通的「另存为覆盖」变成了带撤销历史的编辑器。

- **必须开启桶版本控制**，历史版本保留 30 天（由生命周期规则管理），当前版本不设过期。
- 为什么必须有：uid 是半公开标识（见 `crypto-spec.md` 第 5 节），协议层无法阻止别人用你的 uid 覆盖或清空对象。加密保证了他**读不到**，但保证不了他**写不坏**——版本控制就是这条的兜底。
- 客户端**不**依赖版本控制做任何正常逻辑（不读旧版本、不做乐观锁），它纯粹是运维兜底。
- 运维动作：控制台按 `VersionId` 回滚单个对象；`PUT` 响应回带的 `rev` 即 `VersionId`，出问题时可直接定位。
- 代价：历史版本占存储，由生命周期规则把存储量封顶（快照体积小，实际可忽略）。

## 4. 抗滥用三道闸

> 设计原则（用户裁定）：**上限放宽，超限给提示，不做硬拦截式体验伤害。** 目标是把「零成本 + 不可被当免费存储用」锁住，而不是把正常用户挡在门外。

### 闸一 · 键空间白名单（防「变成网盘/图床」）
- 键只能由服务端按 uid 派生（第 2 节）。
- 请求体必须是符合 `sync-protocol.md` 的**信封 JSON**：字段白名单 + 版本白名单，出现未知字段即 400。
- `Content-Type` 必须为 `application/json`；拒绝 `multipart/form-data` 与二进制。
- 体积上限 **512KB**，超出 413。**不设条目数上限**（本期免费方案的明确裁定）。
- 效果：函数在协议层面就无法保存图片、音视频或其他任意文件。

### 闸二 · 频率与日配额
| 门禁 | 阈值（宽松档） | 超限行为 |
|---|---|---|
| 同 uid 写最小间隔 | 10s（读每 uid 的账本对象 `sync/{p}/{uid}.meta.json`，内含 `{lastWriteAt, day, writes}`；**需要额外一次读**） | 429 + 可读提示 |
| 同 uid 每日写次数 | 200 次 | 429 + 「今日同步次数已达上限，请联系铭」 |
| 函数最大并发 | 小值（如 10），锁死刷量成本 | 平台自然排队/拒绝 |

阈值刻意宽松：正常用户 1–10 次写/天，离 200 次很远；真正被挡住的只有脚本刷量。

### 闸三 · 告警与熔断（人工兜底）
- 配置**费用告警**（如余额/日费用阈值）与**日调用量告警**（如 >5000 次/天）。
- 告警触发后人工在控制台暂停函数或收紧并发；这是最后一道闸，不自动化。

### 明文不进日志
- 函数**不得**打印请求体、响应体或 `ct` 到 CLS。只允许记录：状态码、uid 前 2 位、字节数、耗时。
- 副作用：省 CLS 费用，同时避免密文与元数据被留存。

## 5. 成本模型

**口径更正**：腾讯云官方《免费试用额度》文档写明「开通使用云函数三个月后的用户每月不再享受免费试用额度，**采用按量计费模式**」，**没有**固定的月度套餐扣费。此前讨论中引用的「12.8 元/月基础套餐」来自第三方博客，与官方文档不符，以官方文档为准。用户已确认账号**已过三个月免费期** → 全部按量计费。

### 单价（官方《云函数基本能力产品定价》，2025-03-24 版）

| 计费项 | 单价 |
|---|---|
| 调用次数 | 0.0133 元/万次 |
| 资源使用量 | 0.00011108 元/GBs |
| 外网出流量 / Web 函数响应出流量 | 0.80 元/GB（中国大陆，ap-guangzhou） |

### 本项目量级估算（按 100 活跃用户，60 万次调用/月）

| 项 | 计算 | 月费 |
|---|---|---|
| 调用次数 | 60 × 0.0133 | ≈ 0.80 元 |
| 资源使用量 | 60 万次 × 0.128GB × 0.06s ≈ 4600 GBs | ≈ 0.51 元 |
| 出流量（**未做 304 短路**） | 每次回 50KB → 30 GB | ≈ 24 元 ← 唯一有感的项 |
| 出流量（**做了 304 短路**，目标形态） | 绝大部分 GET 返回无 body 304 → ≈ 0.2 GB | ≈ 0.16 元 |

**结论**：真正决定账单的是**出网流量**，不是调用次数。所以 `sync-protocol.md` 第 5.1 节把 `If-None-Match` / 304 短路列为**必须实现**而非可选优化——它是把月费从「几十元」压到「一元出头」的那一个开关。在 304 短路到位的前提下，个人自付的月费在**一元以内**。

**存疑项**（不改变量级结论，但上线后应核对账单）：官方在 Web 函数下列了「外网出流量」与「响应出流量」两个计费项，**前者是否与后者叠加计费未在文档中明确**。若叠加，上表出流量一行翻倍，仍在「几元以内」量级。核对方式：上线两周后看 COS + SCF 实际账单。

COS 侧：存储每用户数 KB–数百 KB（总计 <1GB），请求量与 SCF 同量级，费用同样在角分量级；新用户 50GB 免费额度若仍在有效期内则存储为 0。

**真正的风险不是单价，是被刷。** 这由第 4 节的闸二（频率与日配额）与闸三（告警）覆盖。

## 6. 部署

- 新建函数 `IIROSE-MEDIA-SYNC`（ap-guangzhou），Node 运行时，与 COS 同地域以走内网。
- CI 沿用现有 `.github/workflows/webpack.yml` 的 build → deploy 两段式，新增 `scripts/deploy_sync.py`（沿用 `scripts/deploy_scf.py` 的「替换产物、保留包结构、上传并验证」思路）。
- 凭据继续走 GitHub secrets（`TENCENT_SECRET_ID` / `TENCENT_SECRET_KEY` / `SCF_NAMESPACE`）。
- **函数 URL 本身不携带任何秘密**，可公开；安全性完全由 uid 分区 + 加密 + 三道闸承担。
- 部署顺序：先手工创建 COS 桶与函数骨架并验证接口联通，再接入 CI 自动化，避免首次自动部署无桶可用而失败。
