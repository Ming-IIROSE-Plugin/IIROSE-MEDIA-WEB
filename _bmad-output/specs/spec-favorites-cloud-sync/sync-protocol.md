# 同步协议 (sync-protocol.md)

SPEC.md 中 CAP-2 / CAP-3 / CAP-4 / CAP-5 的载荷契约。加密参数见 `crypto-spec.md`，端点实现见 `backend-architecture.md`。

## 1. 传输信封 (Envelope)

服务端能看到的全部内容。除这些字段外**不得**出现任何其他字段。

```json
{
  "v": 2,
  "alg": "AES-GCM-256",
  "kdf": { "alg": "PBKDF2-SHA256", "iter": 310000, "salt": "<base64, 32B>" },
  "wrapped": { "iv": "<base64, 12B>", "ct": "<base64, KEK 包住的 DEK||GCM tag>" },
  "iv": "<base64, 12B>",
  "ct": "<base64, 密文||GCM tag>",
  "updatedAt": 1792357121000,
  "itemCount": 152,
  "writer": "<设备随机 id, hex 16>"
}
```

| 字段 | 语义 | 备注 |
|---|---|---|
| `v` | 信封版本 | **服务端必须同时接受 1 与 2**；`1` 为历史格式，读取后由客户端一次性迁移为 `2` |
| `kdf` | 派生 **KEK** 的参数 | `salt` 首次启用时随机生成；被包裹的 DEK 随信封走，salt 与之一致 |
| `wrapped` | 被 KEK 包裹的 **DEK** | **仅 v2**。AAD 绑定 `uid|v|"dek"`，防止被换到别的信封/用户下 |
| `iv` / `ct` | 用 **DEK** 加密的快照 | AAD 绑定 `uid|v|updatedAt`（与 v1 相同） |
| `updatedAt` | 快照逻辑时间戳 | LWW 依据；服务端校验为整数且单调不减 |
| `itemCount` | 明文条目数 | 仅供 UI 提示，不参与判定 |
| `writer` | 写入设备随机 id | 仅用于冲突提示 |

**v1（历史格式）**：无 `wrapped` 字段，`ct` 由「口令直接派生的密钥」加密。客户端读到 v1 时必须走一次性迁移：用口令派生旧密钥 → 解密 → 生成新 DEK → 用 DEK 重加密 → 以 v2 上传。**迁移前后云端旧对象不会被删除，靠版本控制可回滚。**

## 2. 明文快照 (Snapshot)

`ct` 解密后的结构，**永不出端**。

```json
{
  "version": 2,
  "updatedAt": 1792357121000,
  "items": [
    { "key": "netease:song:186016", "record": { /* FavoriteRecord */ }, "deletedAt": null },
    { "key": "bilibili:video:BV1xx411c7mD", "record": null, "deletedAt": 1792350000000 }
  ]
}
```

- `key` = 复合主键 `platform:type:rawId`，由现有 `FavoritesStorageService.deriveFavoriteId()` 产出，设备无关。
- 墓碑条目 `record` 为 `null`，只保留 `key` 与 `deletedAt`。
- `version` 是快照自身版本（与 IndexedDB version 不同），用于合并算法演进。

## 3. HTTP 接口

基址：`https://<function-url>`。全部为 JSON，自带 CORS 头，不经 CORS 代理。

| 方法 | 路径 | 请求体 | 响应 | 说明 |
|---|---|---|---|---|
| `GET` | `/v1/favorites?uid=<uid>` | — | 200 `{"snapshot": <Envelope>\|null}` | 无数据时返回 `snapshot: null`，不返回 404 |
| `GET` + `If-None-Match: <rev>` | 同上 | — | **304，无响应体** | 云端未变化时短路，**出网流量优化主手段**（见第 5.1 节） |
| `PUT` | `/v1/favorites?uid=<uid>` | `<Envelope>` | `{"ok":true,"updatedAt":<ms>,"rev":"<COS VersionId>"}` | 整包覆盖式写入；返回的 `rev` 由客户端保存，用于下次 `If-None-Match` |
| `DELETE` | `/v1/favorites?uid=<uid>` | — | `{"ok":true}` | 清空云端（CAP-7），写空快照而非删除对象，保留版本历史 |
| `OPTIONS` | 任意 | — | 204 | 预检：允许 `GET,PUT,DELETE,OPTIONS`、`Content-Type`、`If-None-Match` |

**错误码**

| 状态 | 场景 | 客户端行为 |
|---|---|---|
| 400 | uid 不合法 / 信封字段校验失败 / 未知 `v` | 提示内部错误，不上报重试 |
| 413 | 请求体 > 512KB | CAP-6：「云端收藏包已满 512KB，请联系铭」 |
| 429 | 触发频率上限 | CAP-6：「操作太快，请稍后再试」；本地数据不动 |
| 503 | COS 不可用 / 函数异常 | 「同步服务暂时不可用」，标记 `dirty` 待重试 |

**冲突（HTTP 层）**：服务端不做合并。若 `PUT` 携带的 `updatedAt` 早于服务端现存对象的 `updatedAt`，返回 409 并回带服务端 `updatedAt`；客户端据此决定是否改用服务端版本或强制覆盖。该分支用于两台设备几乎同时写入的兜底。

## 4. 合并规则

### 4.1 首次启用（CAP-3）

1. `GET` 云端快照；若为 `null`，直接以本地全量上传，跳过预览。
2. 按 `key` 做并集。
3. 同键同时存在于两侧：保留 `createdAt` **更早**的一条；若相等，保留本地（避免无意义抖动）。
4. 呈现预览：「云端 N / 本地 M / 合并后 K」，用户确认后才 `PUT`。
5. 「以本地为准覆盖云端」是**非目标**：服务端对 `updatedAt` 倒退的写入直接 409，客户端不提供该选项，只做并集确认。

### 4.2 稳态

- **逐键并集，而非整包 LWW**：以复合主键做并集，同键由 `resolveConflict` 裁决——两侧都是活记录取 `createdAt` 更早，一侧墓碑则比较 `deletedAt` 与另一侧 `createdAt`。整包的 `updatedAt` 只用于 409 判定与「本地是否比快照更新」的跳过判断，**不参与胜负**。
- 写入前先 `GET` 比对：服务端 `updatedAt` 更旧则本地写；更旧时按 409 处理（先落地服务端版本再合并本地增量）。`writer` 目前**只写不读**，协议不再依赖它做分支判断。
- 上传后把新 `updatedAt` 记入本地设置（`sync.lastSyncAt`）。

### 4.3 墓碑生命周期

- `remove()` 不物理删除，改为写入 `deletedAt`，并置 `dirty`。
- 墓碑参与一切合并：只按 `key` 比较 `deletedAt` 与另一侧的 `createdAt`/`updatedAt`，较晚的操作胜出。
- 本地满 30 天的墓碑在下一次写事务中物理清除；清除**不**单独触发上传（服务端的墓碑随下次全量快照自然消失）。
- 同一 `key` 被「删除后重新收藏」时，写入新记录并清除 `deletedAt`，`createdAt` 更新为新时间。

## 5. 请求量模型

| 动作 | 触发 | 单人频率 |
|---|---|---|
| `GET` | 插件激活/登录后首次、手动「立即同步」、插件 UI 打开、标签页重新可见、窗口获得焦点（后三者按 60 秒冷却）、UI 打开期间每 5 分钟 | 8–30 次/天 |
| `PUT` | 收藏增删后 5s 防抖合并为一次 | 1–10 次/天 |
| `DELETE` | 用户显式清空云端 | ≈0 |

合计 8–30 次/天/人（命中的绝大多数是 304，出网约 200 字节）。**明确排除**：后台轮询、WebSocket、常驻连接、每条收藏一次请求。

### 5.1 出网流量是唯一值得优化的成本项

按量计费下，请求次数费与资源使用量费都是零头，**外网出流量才是主成本项**（约 0.80 元/GB）。因此：

- **必须实现 `If-None-Match` / 304 短路。** 稳态下用户绝大多数 GET 落在「云端没变」，此时只回一个无 body 的 304，出流量趋近于 0。这是把成本压到零头的最关键一条，不是可选优化。
- 客户端在 `PUT` 成功后保存响应里的 `rev`（COS `VersionId`），后续 GET 都带上。
- **已知并接受的取舍：** 信封用 JSON + base64 承载密文，二进制体积会膨胀约 33%。改用二进制体 + 头部传元数据可以省下这部分，但会让函数与客户端的编解码都复杂一档，而 304 短路后剩余的 body 传输量已经很小。**本期保持 JSON+base64，把它记为有意识的取舍而非疏漏**；若日后账单显示出网流量异常，这里是第一个该改的地方。
- 密文是近随机数据，gzip 无效——不要指望压缩来省流量。

## 6. 客户端状态机

```
未启用 → (用户启用 + 设口令 + 解锁成功) → 已解锁
已解锁 → (GET 返回 null) → 首次上传
已解锁 → (GET 返回快照) → 首次合并预览 → 确认 → 已同步
已同步 → (本地变更, 5s 防抖) → 上传中 → 已同步
已同步 → (激活/手动) → 拉取中 → 已同步
已同步 → (用户关闭同步) → 未启用（本地数据保留）
任何状态 → (解密失败) → 锁定：提示口令错误，禁止 PUT
```
